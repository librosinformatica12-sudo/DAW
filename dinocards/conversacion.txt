--- PREGUNTA 1: ESTRUCTURA DEL BACKEND ---
Tres capas: src/ (datos+logica) -> php/ (endpoints) -> paginas
(HTML). Todo entra por require_once src/AccesoDatos.php que abre
sesion, crea la conexion y da escapar()/pedir_login().
Extra: ReglasColeccion.php no toca la BD porque son funciones
puras, testables sin MySQL.

--- PREGUNTA 2: LOGIN Y REGISTRO ---
1) index.php:89-166 -> dos formularios (#form-login, #form-registro)
   con action="php/login.php" y hidden "accion". Pestanas sin
   recarga con mostrarPestana().
2) script.js:140-168 -> e.preventDefault(), fetch con FormData
   (enviarFormulario :115), res.json(), mostrarAviso(), y si ok
   setTimeout 1s -> window.location.href="inicio.php".
3) php/login.php -> header JSON, metodo POST (sino 405),
   prepared SELECT ... WHERE email = ? OR username = ? LIMIT 1,
   bind_param("ss"), password_verify().
4) Sesion -> session_regenerate_id(true) (anti session fixation),
   $_SESSION["usuario_id"] y $_SESSION["usuario"]. Las paginas
   protegidas llaman pedir_login().
5) registro.php -> validaciones, duplicados con num_rows > 0,
   password_hash($clave, PASSWORD_DEFAULT) + INSERT preparado.
6) cerrar.php -> $_SESSION=[], borra cookie (time()-42000),
   session_destroy(), Location: ../index.php.

--- PREGUNTA 3: LOGICA DE NEGOCIO, MD5 Y ERRORES ---
a) Validaciones en servidor: registro.php lineas 24-38 (vacios,
   usuario>=3, filter_var email, contrasena>=4, coincidencia).
   El JS (script.js:183-198) las replica pero manda el servidor.
b) md5 en login.php:50:
   if (password_verify(...)) ok moderna
   elseif (strlen($guardado)===32 && hash_equals($guardado, md5($clave)))
     -> acepta hash antiguo de 32 caracteres y lo MIGRA automaticamente
        a password_hash con un UPDATE.
   Como verlo: tabla usuarios.password_hash -> antiguos hex de 32
   caracteres (81dc9bdb52d04dc20036dbd8313ed055 = md5 de "1234"),
   nuevos empiezan por $2y$. md5 es rapido y vulnerable a rainbow
   tables; hash_equals evita el timing attack.
c) Errores: conexion -> mysqli_report(MYSQLI_REPORT_OFF) +
   connect_errno -> die(). Negocio -> responder(false, "mensaje")
   JSON -> mostrarAviso() en rojo. Red -> catch en JS. Para verlo:
   F12 -> Network -> Response, o la caja #aviso-login en rojo.

--- PREGUNTA 4: LIMPIEZA DE ACCESO MYSQL ---
Todas las consultas con datos de entrada usan prepare() +
bind_param("i"/"s") -> previene SQL Injection (ejemplo:
ColeccionService.php:17-23 con INSERT ... VALUES (?, ?, NOW())).
Concatenacion solo donde se saneo antes: dinosauriosPorIds usa
array_map('intval', $ids) ("son numeros, no hay peligro") y los
LIMIT van con max(1, min(50, $n)).
Complementos: set_charset('utf8mb4') para tildes/ñ, y escapar()
(htmlspecialchars) en la salida ESO es contra XSS, no contra SQL.

--- PREGUNTA 5: PROCEDIMIENTOS ALMACENADOS (4) ---
Parametros IN/OUT; OUT: 0 = OK, negativos = error.
1) Login(IN usuario, IN password, OUT res) [usuarios]:
   vacio -1, contrasena vacia -2, credenciales mal -3, OK 0 + fila.
2) Registro(IN username, IN email, IN password, OUT res) [usuarios]:
   vacio -1, duplicado LIKE -2, contrasena vacia -3,
   si no INSERT con SYSDATE() -> 0.
3) ObtenerColeccion(IN usuario_id, OUT res) [colecciones]:
   devuelve dinosaurio_id ordenados ASC.
4) AnadirNuevaCartaAColeccion(IN usuario_id, IN carta_id, OUT res)
   [colecciones + usuarios]: valida usuario (-1) y dinosaurio (-2),
   luego INSERT en colecciones + UPDATE ultima_obtencion -> 0.
   Ventaja: operacion atomica en la BD.
Por tabla: usuarios (Login, Registro), colecciones (ObtenerColeccion,
AnadirNuevaCartaAColeccion), dinosaurios consultada para validar.
Nota honesta: el PHP actual usa prepare() desde src/ en vez de CALL;
la logica fuerte de validacion vive en los procedimientos.

--- PREGUNTA 6: VIAJE DEL DATO ---
A) JSON (login/registro): submit -> e.preventDefault() -> fetch
   POST FormData -> PHP valida/sesion -> responder() imprime
   {ok, mensaje} y exit -> res.json() -> mostrarAviso() ->
   si ok setTimeout 1s -> location.href = "inicio.php".
B) Sobres (POST -> REDIRECT -> GET): form POST ->
   php/cartaDiaria.php (esta_logueado, REQUEST_METHOD,
   segundosRestantes con espera 86400 s) -> si toca:
   dinosaurioAleatorio() + anadirCarta() + marcarUltimaObtencion()
   -> guarda el resultado en $_SESSION["sobre_flash"] ->
   header("Location: ../inicio.php") -> inicio.php lee y borra el
   flash y pinta. El redirect evita que F5 reenvie el formulario.
   Contadores: data-espera en el boton -> setInterval de 1 s ->
   clearInterval y habilita al llegar a 0.

--- PREGUNTA 3: NAVEGACION VISTAS (TRADICIONAL vs SPA) ---
Tradicional: cada vista es un .php distinto, los <a href> provocan
peticion nueva y recarga completa; menu.php sabe la pagina actual.
SPA: una sola pagina, el JS cambia el contenido con fetch +
innerHTML + history.pushState sin recargar.
Proyecto hibrido (respuesta ideal): navegacion por recarga entre
inicio/coleccion/dinopedia/perfil + mini-SPA en index (pestanas y
hero sin recarga) + login/registro por fetch con redirect de JS +
sobres con POST-Redirect-GET del servidor.

Tecnicas: variables, Flexbox, Grid responsive, sticky, gradientes,
